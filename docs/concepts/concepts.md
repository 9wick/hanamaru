# 設計思想

hanamaruは、targetの契約を検証するテストフレームワークです。正しいテストを書きやすくすると同時に、正しくないテストを書きにくく、構造的に禁止できるものは書けなくします。

対象・条件・期待を素直に表現できることと、用途外の記述をAPIが許さないことを両立します。[契約をテストするためのUX/DX](../guides/testing-contracts.md)が実装の受け入れ条件です。制約は注意書きだけで済ませず、型とAPIの構造へ反映します。

## 契約を検証し、実装方法を固定しない

契約は成功・失敗を含めtarget側にあります。内部のどの関数を何回呼ぶかを、テストの都合で契約へ追加しません。targetを固定しても、その依存を実際に動かして効果を観測できます。

純粋関数は入力と結果、副作用を持つ対象は外部の状態やactionも観測します。メール送信の責任なら、メール到着を確かめることが基本です。mockや呼び出し確認は直接観測が困難な場合の妥協であり、妥協するほど実装を固定します。

対象の特性はpure/effectful、ケースの種類はit/propertyです。関係は性質の表現の一つ、状態・actionは観測対象です。expectは各ケースの中で期待を書く操作で、propertyと並べる種類ではありません。一ケースで全責任を検証することや、別の契約スキーマをアプリへ追加することは要求しません。

## まず、テストを書くだけでよい

<!-- example: docs/examples/math.test.ts -->
```ts
import { Test, registerTest } from 'hanamaru'
import { add } from './math.ts'

export const addition = new Test()
  .target(add)
  .it('2つの数を足す', t => t.args(1, 2).expect(e => [
    e.result.toBe(3),
  ]))

registerTest(addition)
```
出典: [docs/examples/math.test.ts](../examples/math.test.ts)

ケースには人が読む名前を付け、対象には実際の関数を渡します。
代替が必要な場合は、環境が提供するinfra境界から選びます。
プラグイン向けのblueprintを作るために、それらをID・ソースパス・別名としてもう一度書かせません。

`.it(name, body)`、`toBe`、`toEqual` など、既存のテストで親しんだ語彙を使います。
Vitest/JestのAPI全体との互換性は提供しません。
[Vitestのtest API](https://vitest.dev/api/test)と[JestのAPI](https://jestjs.io/docs/api)を参照してください。

## チェーンが型を積み上げる

`.target()` で引数と戻り値、`.use(...)` のmiddlewareでコンテキストが決まります。
呼び出しの検証では、`c.boundary(c.ctx.outbound)` のBoundaryから境界の引数型が決まります。
通常は型パラメータを手書きせず、エディタ上で次に書ける内容が絞られます。
独立した子が親のコンテキストを使う場合だけ、必要な型を宣言します。

ケースやgroupを追加した後は、既存の定義の前提になる設定を変えられません。
正常・例外の期待を矛盾させたり、引数を確定せずに検証を書いたりする操作も型で防ぎます。
プロパティの差し替え可否など、TypeScriptで表現できない条件は実行時に検査します。[型推論](../reference/type-inference.md)に範囲を記載しています。

## ケースは独立した実行単位

各test caseは、他のcaseが実行されたか、実行されなかったか、どの順序で実行されたかに依存しないものとして定義します。
宣言順は表示とblueprint上の順序であり、利用者が意味を持たせる実行順ではありません。
標準実行器の初版は直列に実行しますが、将来のshuffle・並列実行・複数processへの配置で順序や配置が変わっても、caseの意味が変わらないことを前提にします。

`use(...)` のmiddleware、mock、コンテキスト、呼び出し記録は各評価で作り直します。propertyは生成例・縮小候補ごとに評価を分離します。
利用者がprocess.env、module state、global、外部DB等を変更する場合も、別caseの実行結果へ依存せず、必要な初期化と復元をそのcaseの実行境界で行います。
高価な環境の共有と、case間の意味的な依存は別の問題として扱います。

順序を持つ一連の操作は通常のcase同士の依存として表さず、scenarioをtargetにしたit/propertyのstepsとして表現します。
scenario内の操作は順序を持ちますが、ケース全体は他の独立した実行単位との順序に依存しません。

## 結果・状態・actionを観測する

純粋関数では入力と結果を照合します。副作用を持つtargetでは、保存状態や今回のメール到着など、契約に対応する効果を観測します。実行前後の値、出来事の記録範囲、完了条件を評価に結び付け、取得失敗を不在と混同しません。

直接観測できない場合の呼び出し確認は、環境が許可したinfra境界に限定します。記録する対象を定義から得て、実行前に記録を開始し、実行後に検証・復元します。任意の内部関数を指定するspyや、呼び出し記録を効果の観測として扱う入口は提供しません。

[期待と観測](../reference/api-expect.md)で、用途ごとの記述を定めます。

## 定義と実行を分ける

テストコードは完成した定義をregisterTestへ登録します。CLIが対象ファイルを読み、登録から実行対象を選びます。
単体実行も対象のID・名前・宣言位置で指定し、runnerが計画とworkerへの指示を取りまとめます。

実行時の構造は、一回のrun全体 → group → 対象ケース群 → ケース → 試行 → 評価です。groupは省略でき、入れ子にもできます。対象ケース群は一つのテスト対象と、その対象を検証するケースを持ちます。
この流れと実行時の階層は、別の見方です。


プラグイン作者は `.blueprint()` から、テスト定義を構造化した値を取得できます。
「何を対象に、どう準備し、どの振る舞いに置き換え、何を渡し、何を検証するか」を保持します。
プラグインはケース名や宣言位置などのmetadataをここから読めます。

blueprintには関数やオブジェクト参照も含みます。JSONに変換できることは要求しません。
middlewareで用意する値に依存する引数や結果の期待は、それを組み立てる関数として保持します。
検証条件はビルダーとして保持し、環境準備後・target前のcompileで構造化します。実測値はtargetと観測の後に取得し、照合します。
任意の関数内部を解析して、まだ評価していない値まで取得できるとはしません。
[プラグイン向けblueprint](../reference/metadata.md)で、保持する構造と評価時点を定めます。

## 関連するテストをグループにまとめる

`group([children])` で一つ以上の子をまとめ、use・timeout・retryの適用範囲を作ります。
必要なら `group(name, [children])` でグループに名前を付けられますが、名前は必須ではありません。
親の設定を配下のケースへ適用します。境界の代替は子のeffect/scenarioケースにだけ置き、groupから注入しません。
middlewareは親から子へコンテキストを渡し、後処理は逆順です。コンテキストと呼び出し記録は各ケースの評価ごとに用意します。

高価な資源を配下全体で一度だけ用意する場合は、`group(middleware, [children])` でまとまり全体をmiddlewareで囲みます。通常のuseは各評価（propertyの生成例・縮小候補を含む）、group middlewareは子のまとまり全体という実行境界がAPI構造から分かれます。

ビルダーはイミュータブルです。グループへ追加しても元の子の定義は変わりません。
blueprintには各階層の設定と子の関係を保持します。
[テストをグループにまとめる](../guides/grouping.md)に例と契約を示します。

## middlewareでケースを囲む

`.use(middleware((ctx, next) => ...))` で、資源の取得と解放を同じスコープに書けます。
`return await next({ db })` で後続へ値と型を渡し、finallyで片付けます。
値を渡すだけなら、`middleware(async (_, next) => next({ expected: 3 }))` と書けます。
middleware自身の前処理期限・後処理期限もその定義に書きます。[middlewareの例](../guides/middleware.md)を参照してください。

## 設定とケースの入口

timeout・retryは下流へ引き継ぐ実行設定です。項目ごとに継承し、内側の指定で上書きします。
itは一ケース、eachは行ごとのケースを定義する入口です。同じ設定の規則と型付きの期待を使います。
結果には位置と各試行、条件・期待・観測・原因を残し、実行前のblueprintと対応させます。

## 軽量さ

利用者が契約を書くために必要な入力・観測・期待を、小さな記述で表せることを重視します。型・ID・呼び出し管理を重ねて書かせず、実装側の都合でUX/DX契約を弱めません。
TypeScriptの型チェックは既存の開発環境に任せます。
実装状況と初版の範囲は[制約](../reference/limitations.md)を参照してください。
