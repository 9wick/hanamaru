# 用語集

hanamaruのドキュメントとAPIで使う語の意味を定めます。
同じ語でも文脈が違えば意味とルールが変わるため、各語に文脈とルールを書きます。
他の文書と食い違う場合は、この用語集に合わせて直します。

## 定義から実行まで

### テスト定義

- 識別子: `new Test()` から始まるチェーン
- 定義: テストを書く人が、対象・ケース・条件・設定をコードで定義すること、およびそのコードで書いた内容。
- 文脈: 利用者がテストを書くときに使います。
- ルール: コードを評価して得られる値とは区別します。

### 完成した値

- 識別子: ケースまたは子を追加し終えたチェーンの戻り値。現行の型名は `TestDefinition<R>`。
- 定義: `run(test)` に渡す、対象ケース群またはグループの完成したビルダーの値。
- 文脈: 利用者はこの値を直接実行器に渡すか、グループの子として追加します。
- ルール: チェーンの途中の値は実行できません。親から必要なコンテキストの型も保持するため、親なしで実行できない完成値もあります。

### blueprint

- 識別子: `test.blueprint()`、`TestBlueprint`、`SuiteBlueprint`、`GroupBlueprint`
- 定義: テスト定義から得られる、ケースやグループ、設定、関数参照などの実行前の構造。
- 文脈: プラグイン作者が定義内容を読むための準公開APIです。通常の利用者は完成したテストを `run(test)` に渡します。
- ルール: blueprintを取得してもmiddlewareやテスト対象は実行しません。関数やオブジェクト参照を含むため、JSONで往復できることは保証しません。blueprint自体は `run()` の入力ではありません。

### 実行計画

- 定義: 実行器がblueprintをもとに決める、ケースの実行方法。
- 文脈: `run(test)` の内部で使う概念です。
- ルール: blueprintと区別します。実行計画を取得したり、`run()` に直接渡したりする公開APIはありません。

## ケースの実行

### 対象ケース群

- 識別子: `.target()` に続けて `.it()` / `.each()` / `.only()` / `.skip()` / `.todo()` でケースを追加した完成値。現行の型名は `Suite`、blueprintの型名は `SuiteBlueprint`。
- 定義: 一つのテスト対象と、それを検証する一件以上のケースを持つ単位。
- 文脈: テストを書く人は対象ケース群を直接 `run()` に渡すか、`.group()` で作るグループへ追加します。
- ルール: `.group()` で包まない限りグループではありません。実行時の階層は、実行器 → 任意のグループ（入れ子可）→ 対象ケース群 → ケース → 試行です。

### グループ

- 識別子: `.group([children])`、`.group(name, [children])`、middlewareを伴う同じ形。
- 定義: 一つ以上の対象ケース群やグループを束ね、共通設定の範囲を作る構造。
- 文脈: テストを書く人が複数の子、または一つの子を明示的なまとまりにするときに使います。
- ルール: 一回の `.group()` は空でない子配列を一つの子グループにまとめ、親へ追加します。子が一つでも配列で渡します。ルートグループ自身は無名です。`group(name, [children])` の名前は、そのまとまりを親へ追加した箇所の表示名です。名前を省略すると追加箇所も無名になり、元の子自身の名前は変わりません。

### テスト対象

- 識別子: `.target(fn)`、`.target(name, fn)`、`.target(obj, key)`、`.target(name, obj, key)`、`SuiteBlueprint.target`
- 定義: ケースが引数を渡して呼び出し、戻り値または例外を検証する関数・メソッド。
- 文脈: テストを書く人が、ケースで確かめたい振る舞いを指定するときに使います。
- ルール: `.target()` で指定した関数・メソッドを、その後に追加する各ケースが呼び出します。名前を付けるなら第一引数に渡し、省略時は関数名・メソッド名を対象ケース群の表示名に使います。モックや呼び出しの検証で指定するメソッド、CLIが選ぶファイル・ケースとは区別します。`.target()` は指定する操作、`SuiteBlueprint.target` はblueprintに残す参照です。結果の `phase: 'target'` は呼び出し段階を示します。

### コンテキスト

- 識別子: `Ctx<…>`、middlewareの `ctx`、`argsFrom(ctx => …)`、`e.ctx`
- 定義: middlewareが `next(fields)` へ渡した値を、後続のケースで参照するために重ねたもの。
- 文脈: テストを書く人が、用意した資源や期待値などを後続のmiddleware・引数・期待から使うときに参照します。
- ルール: 同名のフィールドは後から渡した値で置き換えます。timeout・retryの実行設定はコンテキストのフィールドではありません。文章では「コンテキスト」、コードでは `ctx` / `Ctx` と書きます。

### 実行設定

- 識別子: `.timeout(ms)`、`.retry(count)`、`ExecutionConfig`、`ResolvedExecutionConfig`
- 定義: ケースの試行期限と再試行回数を決める設定。
- 文脈: 共通設定はgroupや `.target()` の前後に、個別設定はケースに書きます。実行時に配下のケースへ適用します。
- ルール: 項目ごとに外側から内側へ継承し、内側の指定で上書きします。middlewareが渡すコンテキストとは別に保持します。

### 試行（attempt）

- 定義: ケースを1回実行すること。retryで再実行するたびに新しい試行になります。
- ルール: middleware・モック・コンテキスト・呼び出し記録は試行ごとに作り直します。

### 試行期限（timeout）

- 識別子: `.timeout(ms)`
- 定義: ケースの1試行にかかる時間の上限。試行を囲むmiddlewareの前処理・後処理も含みます。
- 文脈: groupや `.target()` の前後、ケースに書けますが、どこに書いても配下ケースの試行期限を指定しているだけです。
- ルール: groupやテスト対象そのものに期限はありません。groupで指定しても、グループ全体の合計時間にはなりません。
- 使わない語: 「groupのtimeout」「targetのtimeout」。書いた場所ではなく、制限する実行（試行）で呼びます。

## 検証の語彙

### 期待

- 定義: テスト対象の戻り値・例外・呼び出しについて、望む振る舞い。
- 文脈: テストを書く人が、何を保証したいか説明するときに使います。
- ルール: 期待そのものと、それを確かめる個々の検証条件を区別します。

### 検証条件

- 定義: 実際の値や呼び出し記録と照合する一件の条件。
- 文脈: `.expect()` や `.expectCalls()` に並べ、実行時に一件ずつ評価します。
- ルール: 一つの期待に複数の検証条件を使えます。

### マッチャ

- 識別子: `toBe`、`toEqual`、`calledTimes` など。
- 定義: 検証条件の照合方法を選ぶ操作。
- 文脈: テストを書く人が条件を記述するときに呼びます。
- ルール: マッチャを呼ぶ時点では照合せず、記述子を作ります。

### 記述子

- 定義: 実行前に保持する、照合対象・マッチャ・期待値などを表す構造。
- 文脈: blueprintが検証条件を保持するときに使います。コンテキストを使う `.expect()` は、記述子を組み立てる処理を実行まで保持します。
- ルール: 実行後の判定である検証結果とは区別します。

### 検証結果

- 定義: 検証条件を実際の値や呼び出し記録と照合した後の判定。
- 文脈: 試行結果で条件ごとの成功・失敗・未評価を示すときに使います。
- ルール: 実行前の記述子と区別します。

## 位置と行

### ソース行番号・データ行番号

- 定義: ソース行番号はケースやグループ追加箇所を書いたソースコードの行、データ行番号は `.each()` に渡した配列内の行の順番。
- 文脈: エラーの場所を示すときはソース行番号、`.each()` のどのデータで失敗したかを示すときはデータ行番号を使います。
- ルール: 文脈から判断できる文章は自然に書けますが、両者を比べる箇所では単独の「行番号」を避けます。ソース行番号と表示用のデータ行番号は1始まり、`row.index` は0始まりです。

## 結果の状態

### 実行指定（mode）

- 定義: ケースを実行対象にするかを定義時に指定するもの。`run` / `only` / `skip` / `todo`。
- ルール: 実行した結果の状態ではありません。

### 試行状態（status）

- 定義: 開始した一試行の結果。`passed` / `failed` / `cancelled`。
- ルール: 成功には失敗記録がなく後処理が完了し、失敗には一件以上の失敗記録があります。

### 未実行理由（notRun）

- 定義: 試行を一度も開始しなかったケースの理由。`skipped` / `todo` / `cancelled`。
- ルール: 試行が一件でもあれば持ちません。ケース全体の成否は試行または未実行理由から導きます。

### runの終了理由（reason）

- 定義: runがなぜ終了したか。`completed` / `timeout` / `interrupted` / `cleanup-failed`。
- ルール: runの成否を示す `status` とは別に保持します。`passed` と組み合うのは `completed` のみ、`cancelled` と組み合うのは `interrupted` のみです。

## middleware

### middleware

- 識別子: `middleware(fn, { timeout })`、`.use(m)`、`.group(m, [children])`、`Ctx<…>`
- 定義: ケースを支える準備と後片付けを、ケースの実行を囲む形で書いたもの。共通の下ごしらえを複数のケースで使い回すために使います。
- 文脈: テストを書く人が、DB・サーバー・テナントなどの前提を整えるときに使います。
- ルール:
  - すべて `middleware()` で作ります。関数をそのまま `.use()` や `.group()` に渡しません。
  - `next(fields)` でケースへ値を渡せます。値を渡さず状態を整えるだけでも構いません。ケースへ値を渡す手段はmiddlewareだけです。
  - 複数のmiddlewareは入れ子になり、後処理は逆順に動きます。
  - `.use(m)` では各試行を囲み、`.group(m, [children])` では子のまとまり全体を一度だけ囲みます。どちらでも同じmiddlewareを使えます。
  - HonoやExpressのmiddlewareと違い、nextを呼ばずに打ち切ることはできません。nextは必ず1回呼びます。nextの失敗をcatchしても、テストの失敗は取り消せません。
  - 単独で定義して上流の値を読む場合は、引数を `Ctx<…>` で包んで要求を書きます。渡す値は書きません（推論されます）。
- 使わない語: setup、fixture。

### Ctx

- 識別子: `Ctx<…>`
- 定義: middlewareが要求するコンテキストの型。利用者が書いたフィールドと、hanamaruがコンテキストへ足すフィールドを合わせます。
- 文脈: 単独で定義して使い回すmiddlewareの引数に書きます。`.use()` / `.group()` へ直接書くmiddlewareでは、文脈から型が決まるので書きません。
- ルール: 要求だけを書きます。型パラメータで要求を書くと、nextへ渡す値の推論が失われます。

### 前処理・後処理（before / after）

- 定義: 前処理はmiddlewareがnextを呼ぶまで、後処理はnextが完了してからmiddlewareが完了するまでの区間です。
- ルール: nextの中でケース（groupではchild）を実行している時間は、どちらにも含めません。
- 使わない語: setup / cleanup、準備 / 後始末。「準備」はmiddleware全体の役割を指す語で、区間の名前には使いません。

### 前処理期限・後処理期限

- 識別子: `middleware(fn, { timeout })` の `timeout`
- 定義: middleware自身が持つ期限。一つの値を前処理と後処理のそれぞれに適用します。
- 文脈: 期限はmiddlewareの性質です。groupや `.use()` の呼び出しではなく、middlewareの定義に書きます。
- ルール:
  - 指定しない場合は、使う場所に関係なく既定値の10,000msを使います。
  - `.use()` で使う場合は、試行期限とmiddleware自身の期限の両方が効きます。
  - `.group()` で使う場合、middlewareはどの試行にも含まれないため、効くのはmiddleware自身の期限だけです。

## モックと呼び出しの検証

### モック（mock）

- 識別子: `.mock(obj, key, m => ...)`
- 定義: メソッドの振る舞いを差し替えること。
- ルール: 呼び出しの検証とは独立しています。検証のためにモックする必要はありません。

### 呼び出しの検証

- 識別子: `.expectCalls(call => [...])`、`call(obj, key)`
- 定義: ケースの実行中にメソッドがどう呼ばれたかを、回数・引数で検証すること。
- ルール: モックしたメソッドにも、モックしていないメソッドにも使えます。モックしていなければ本物のメソッドを呼び、呼び出しだけを記録します。
- 使わない語: `e.mock()`、「モックの検証」。

## 使わない語

| 語 | 理由 | 代わりの語 |
|---|---|---|
| setup | xUnitのsetUpと同じく環境の準備に読めるが、実態は値の提供だった。middlewareの前処理の呼び名とも衝突していた | middleware、前処理 |
| `.setup()` | middlewareの `next(fields)` と役割が重なるため廃止した | middleware |
| fixture | 意味が伝わりにくい | middleware |
| `.describe()` | 対象ケース群の名前とグループ追加箇所の名前を別の操作で指定する必要がない | `.target(name, fn)`、`.group(name, [children])` |
| groupのtimeout / targetのtimeout | groupやテスト対象に期限があるように読める | 試行期限 |
| `e.mock()` | 呼び出しの検証をモックに限定してしまう | `call(obj, key)` |

## 未決の論点

- `TestDefinition` / `Suite` など、完成した値を表す型名の整理。
- `Assertion` / `CallAssertion` など、検証語彙に対応する型名の整理。
- ソース位置の公開型・フィールド名をどうするか。
- 配下の結果から導くグループ・対象ケース群の集約状態を、公開型でどこまで表現するか。
