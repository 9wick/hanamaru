# 契約をテストするためのUX/DX

このページは、hanamaruが満たすべき利用体験と、不適切な書き方を防ぐための実装契約です。正しいテストを書きやすくすると同時に、正しくないテストを書きにくく、構造的に禁止できるものは書けなくします。

本文は設計上の原則です。実際に書く構文・完結した例・禁止例は[契約からテストを書く](writing-tests.md)、用途別の型は[型推論](../reference/type-inference.md)、実行順は[実行セマンティクス](../concepts/semantics.md)に定めます。これらを合わせて実装の受け入れ条件とします。

## 契約を誰が決めるか

契約はtargetの責任です。成功時・失敗時の結果と、副作用についてtargetが約束することをテストします。テストの都合で責任を縮めたり、仕様にない責任を追加したりしません。

メール送信を担うtargetなら、メールが届いたことやメールボックスに存在することを確かめます。「送信関数を呼んだ」は直接観測できない場合の妥協であり、メールが届いたことと同じ保証にはなりません。妥協するほど特定の実装方法を固定します。

targetは責任を問う対象を固定するために指定します。依存先も実際に動かして責任を確かめられます。targetだけを孤立させるための指定ではありません。観測のために取得関数を使うことと、検証対象を別の関数へすり替えることを区別します。

一つのケースは契約の一側面を検証できます。全責任の網羅を一ケースの完成条件にはしません。アプリケーションへ別の契約スキーマを要求したり、関数型から業務上の責任を自動判定したりもしません。

## テストを選ぶ二つの軸

targetで対象、pure/effectfulで特性、it/propertyでケースの種類を選びます。省略時pureは明示pureと同じで、宣言はケース追加前に一度だけです。副作用の有無と具体例/性質は別の軸です。

| 検証対象 | 観測するもの |
|---|---|
| 純粋関数 | 入力に対する戻り値・失敗、入力と結果の関係 |
| 副作用を持つtarget | 戻り値・失敗に加え、外部で生じた状態・action |
| 複数実行・操作列 | 結果間の関係、各段階の状態・出来事とその順序 |

| 検証方法 | 利用者が指定するもの |
|---|---|
| 具体例 | 具体的な入力と、契約が定める期待結果 |
| 性質 | 入力範囲と成立する条件。固定入力ならconstantで範囲を明示 |
| 性質の表現としての関係 | property内で入力・結果・観測値の関係や法則を指定する |

手書きの入力、eachの行、生成入力は入力の選び方です。unit・integration・E2Eは対象範囲の違いであり、許されるマッチャやmockを決めるラベルにはしません。projectの名前から検証方法を変えることもありません。

## 具体的な期待結果を書く

```text
対象: add
入力: 1, 2
期待結果: 3
```

入力と期待値の型はtargetから推論します。利用者は型・対象ID・ソース位置を重ねて書かず、結果の型に合う期待値を直接指定します。

- 具体値の期待を置く場所には、その値との一致を記述します。「0ではない」や任意述語を期待値の代用品として置ける共通マッチャ集合にしません。
- 出力の一部だけが検証対象なら、対象の部分と期待値を明示する別の記述を使います。全体一致と部分検証を区別でき、全体が一致したと報告しません。
- 正常な戻り値とthrow/rejectの期待は区別します。Result型の失敗値は戻り値です。例外については、契約で決まる種別や内容を検証し、スタックや生成位置の一致を一律に要求しません。
- 期待結果が3、実測値が4なら、target・入力・期待値3・実測値4を示します。具体値を指定すべき場所へ述語を渡した場合は、定義の誤りとしてその箇所を示します。

## 性質を記述する

```text
対象: sort
入力: 配列の具体例、または範囲を指定して生成した配列
検証する性質: 結果が昇順である
```

性質は具体値の不足を隠すためのマッチャとしてではなく、検証方法として明示します。入力・結果・観測値のうち、何に対する条件かが定義から分かる形にします。

- 名前を付けただけの汎用expectへはしません。標準で表せる比較・条件は対象の参照を持つ記述とし、任意述語は必要な性質を表す拡張口に限定します。
- 具体例の期待値の欄へ性質の記述を渡すことはできません。逆に、同じtargetに具体例のケースと性質のケースを併設できます。具体例はtarget配下のit、性質は並列のpropertyに書き、期待は各ケースのexpectで表します。
- propertyのforAllで範囲・seed・runs・maxShrinksを指定し、反例を縮小して再現情報と具体的な入力を残します。effectfulでは候補ごとに環境を初期化します。暗黙の入力除外はしません。
- 空の範囲やrunsが0の指定を拒否し、性質を一度も評価できなかった場合は成功にしません。述語の例外も「性質が偽」「targetが期待した例外を投げた」と混同しません。

昇順と要素保存は別の性質として検証できます。昇順のケースだけでソート全体の正しさを保証したとは扱いません。任意述語の意味的な妥当性を型だけで保証することもありません。

## 実行間の関係を記述する

```text
対象: encodeとdecodeの往復関係
入力: こんにちは
実行: encodeの結果をdecodeへ渡す
期待する関係: decodeの結果が元の入力と等しい
```

往復、冪等性、異なる入力に対する結果の関係、参照実装との一致を扱います。一つの関数を複数回呼ぶだけなら、対象を増やす必要はありません。

- 呼べるのは宣言した対象だけです。任意の関数を渡す共通callを用意しません。
- 結果参照はケースと試行に属します。別ケースの結果を持ち込んだり、まだ実行していない結果を実測値として比較したりできません。
- 値の一致・不一致や順序関係は、入力・結果の参照同士の関係として書けます。参照を取得するためだけのIDやsaveAsを要求しません。
- 参照実装との不一致なら、同じ入力と双方の結果を示します。一致しても、参照実装自体の正しさを保証したとは報告しません。

冪等性や往復関係は[propertyのsteps](multiple-calls.md)で対象を限定して実行します。単一targetのitは一回の実行です。scenarioのitは対象集合を固定した具体的な回帰例を許し、任意述語は許しません。複数回の実行そのものを性質と混同しません。

## 副作用を状態とactionから観測する

```text
対象: registerUser
前提: ケース用のDBとメールボックス
入力: Aliceの登録情報
状態の期待: 取得したユーザーが登録情報と一致する
actionの期待: 今回の登録によるメールが1通届き、宛先と本文が一致する
```

状態は保存された値など、観測時点で成立しているものです。actionはメールの到着など、実行区間に起きた出来事です。送信関数の呼び出し記録とは区別します。

準備・targetへの入力・観測・期待を、一つのケースとして読み取れるようにします。環境と後始末はmiddleware等で再利用でき、ケースごとに手書きの実行ハーネスを組ませません。取得関数などの観測手段は利用者が提供でき、その結果型から期待値を推論します。

| 利用者が確かめたいこと | 記述・実行の契約 | 拒否または失敗にするもの |
|---|---|---|
| 実行後の状態 | target完了後に状態を読み、期待と比較する | 読み取りの失敗を空・不在へ変換して成功させること |
| 状態の変化・不変 | 実行前後の観測値を独立して保持する | 同じ可変参照を前後のスナップショットとして扱うこと |
| 今回起きたaction | target開始前から記録し、試行用の範囲を識別する | 過去の出来事や別ケースの出来事を今回の結果として数えること |
| actionの不発生 | 完了条件または有限の観測期間内で発生がないことを確かめる | 一度の未観測を、無期限の不発生として報告すること |

観測の初期化、開始、target実行、必要な待機、照合、後始末の順序を実行器が管理します。結果のIDを引数に取るstateを定義でき、観測をtargetの操作集合へ混ぜません。クラスのtargetはfromで評価ごとのreceiverを供給し、依存をデータ引数へ移すことを要求しません。

比較用の値表現と、述語に渡す型付きのコピーを区別します。[値の比較](../reference/value-comparison.md)はMap/Set/TypedArray/Dateやクラスの公開データを扱い、期待値の保存のために正当な具体例を禁止しません。

state/actionは観測の形、evidenceは証拠の種類です。環境がreal-effect/substitute-effect/call-recordを宣言し、ケースで書き換えられません。フレームワークが観測点の真実性を自動証明するとはしません。観測器は評価ごとの所有者と期間を守り、環境提供者は受信側の履歴と送信口の記録を区別します。

診断には観測先・期間または完了条件・期待・実測を残します。観測そのものに失敗した場合は、その段階と原因を示します。状態が前後で同じことと、途中でactionが起きなかったことは、別の検証です。

失敗時もtargetの契約に従います。「失敗したら通知しない」なら不発生を、「失敗を監査記録へ残す」ならactionや状態を検証します。フレームワークが失敗時の副作用禁止や原状維持を一律に課しません。

## 操作列と時間を記述する

```text
対象となる公開操作: 作成、更新、取得
順序: 作成 → 更新 → 取得
期待: 取得結果が更新後の内容と一致する
```

順序に意味がある操作は一つの独立したケースに収めます。状態を引き継ぐために別々のitを宣言順へ依存させません。操作に名前を付け直す、値へ保存用IDを振る、といった記述は要求せず、実際の値の受け渡しから型を保ちます。

- 公開操作で前提を作ってから失敗する契約は、前段を通常の操作、最後をfinalとして書けます。fakeの内部状態へ直接seedすることは要求しません。前段の例外を最後の期待へ流用しません。
- 操作する対象範囲を明示し、そこから許される操作を絞ります。観測用の読み取りは操作と区別します。
- 単一関数のitに複数実行を追加せず、性質はpropertyのsteps、具体的な操作列はscenarioのitのstepsで記述します。
- 観測の再試行はtargetを再実行しません。通知を待つために登録処理をもう一度呼ぶことはありません。
- ケース全体のretryと観測の待機を区別します。試行timeoutはテスト実行の制限であり、業務上の「一定時間内に反映される」の期待を代替しません。
- 途中で失敗した場合は、実行済みの操作、失敗箇所、未実行の操作を識別します。未実行の期待を成功扱いにしません。

[scenarioのit/property](flow.md)もこの要件に従います。非同期処理の観測期限と完了条件は、何を約束するtargetかに応じて指定します。

## infraの代替と入力条件を整える

環境が依存インターフェースに従った実資源または型付きfakeを用意します。入力に応じる応答と障害を自然に表せ、内部の呼び出し順に結合したstubを強制しません。mock/replace/expectCallsやBoundaryの別レイヤーは設けません。

時計・乱数・外部応答の固定は入力条件の制御です。それだけで出力の証拠がcall-recordになるわけではありません。実効果・代替環境の効果・呼び出しを確認した証拠は、環境が観測点に応じて宣言します。caseから任意メソッドを差し替えるAPIを提供しない一方、任意の利用者コードをsandbox化するとは約束しません。

## 用途を越えた流用を防ぐ

| 記述 | 使える場所 | 許さない流用 |
|---|---|---|
| 具体値の期待 | 結果や観測値の一致 | 否定・任意述語で具体値の期待を置き換える |
| 部分の期待 | 明示した観測範囲 | 出力全体の一致を確認した扱いにする |
| 性質・関係 | 宣言した入力・結果・観測の検証 | itへの性質条件の持ち込み、別ケース・別候補のrefの流用 |
| 状態・actionの観測 | 副作用を持つ対象の試行 | 呼び出し記録を実際の効果として扱う |
| 操作列 | 順序を宣言した独立ケース | 通常ケース間の順序依存、単一関数のitへの自由な複数実行 |
| 環境のfake・観測 | 型付き依存とevidence付きの観測口 | 呼び出しだけの証拠を実効果へ格上げすること |

エディタでは、その時点・用途で使える操作だけを提示します。不適切な組合せは可能な限り型で拒否し、型を経ない入力も実行受付で検査します。動的な観測の失敗は実行時に報告します。注意書きだけで同じ汎用APIを開放する実装では、この要件を満たしません。

任意述語や観測器の内容について、意味的な正しさをすべて証明する保証はしません。拡張口の存在を理由に、標準の入口の制約を緩めることもしません。

## 実装の受け入れ条件

各入口は、成功する例だけでなく、その機能を別用途に持ち込む負例と一緒に検証します。

1. 利用者は対象・前提・入力・観測・期待を、必要な分だけ書ける。アプリ側の契約スキーマや一ケースでの全責任の検証は要求されない。
2. 型が対象から推論され、不要な型注釈・キャスト・ID・手書きの呼び出し管理を要求されない。
3. 禁止した組合せは補完に出ず、通常の型付き利用では定義できない。動的にしか分からない違反は該当する境界で失敗する。
4. 失敗時は、具体値・性質・関係・状態・action・観測障害のどれに問題があるかを区別でき、該当入力と観測値へ戻れる。
5. 実際の効果を確かめる通常の書き方より、mockや呼び出し確認への妥協の方が標準例で優先されない。

メソッド名や記述子の設計は、この利用体験を満たす必要があります。不一致・不変・不発生はそれぞれの用途で表し、具体値の期待を汎用notへ置き換える入口は設けません。[公開構文](writing-tests.md)は利用例と禁止例を対にし、実装では実行例と型の負例で検証します。[開発手順](../../CONTRIBUTING.md#uxdxを先に契約にする)に進め方を記載しています。
