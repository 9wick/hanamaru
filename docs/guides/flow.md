# 操作列の具体例と性質

操作の順序が契約に含まれる場合はscenarioで対象操作を固定します。ケースの入口は他の対象と同じit/propertyです。flowという第三の入口は提供しません。

## 関数の契約とシナリオを分ける

単一関数のitは一回の実行、scenarioのitは一つの具体的な操作列を検証します。propertyは生成入力について性質を検査します。単一関数を複数回呼ぶ法則は[propertyのlaw](multiple-calls.md)で表し、自由なcallsにしません。

## 対象範囲を明示する

`target(scenario({ create, rename, read })).effectful()` のように対象集合と特性を分けて指定します。省略時はpureで、純粋な操作列として扱います。外部状態を扱う集合にはeffectfulを宣言します。特性はケースごとに切り替えません。

## 操作と観測を書く

具体例は `.it(name, t => t.steps(...).expect(...))`、性質は `.property(name, p => p.forAll(...).steps(...).expect(...))` と書きます。[完結した例](writing-tests.md#操作列)に従います。

stepsのs.ctxは環境、propertyだけのs.inputは生成タプルです。宣言した操作の引数と、先行の正常結果refを結び付けます。全操作を宣言順にawaitし、戻り値を使わない操作も省略しません。任意関数の追加や実測値に応じた分岐、asyncの定義コールバックは拒否します。

途中の状態は公開のread操作をstepsへ置き、そのrefを返して検証します。結果は取得時点で保存され、後続の変更に追従しません。refの生の値は次の操作へ渡せますが、検証用の保存値とは別です。

## 待機と再実行

観測は一つの操作列全体を囲みます。完了条件や有限期間を指定し、観測の待機のために操作列を再実行しません。

propertyの各生成例・各縮小候補で環境を作り直します。一候補内の操作間は状態を引き継ぎますが、候補間や通常ケース間には引き継ぎません。共有資源を使う場合も、環境が初期化と範囲分離を提供します。

## 結果と後始末

scenarioは全操作の正常完了を期待します。途中のthrow/rejectは後続を停止する失敗で、error条件で成功にしません。失敗自体の契約は単一targetのit/propertyで検証します。Result型の失敗値は正常結果として扱えます。

実行済み・失敗・未実行と観測条件を対応させ、取得不能や未評価を成功へ変換しません。後始末を完了してから次の候補へ進み、解放不能なら後続を中断します。
