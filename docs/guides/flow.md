# シナリオ全体を検証するflow

flowは、ある前提から一連の操作を行い、期待した振る舞いが成立することを検証する入口として検討しています。
たとえば「未登録の状態からフォームで登録すると、ログインできる」というシナリオです。

**flowは未実装で、具体的な書き方と保証を設計中です。**
このページでは利用目的と検討範囲を説明します。実行できるAPIの案内ではありません。

## 関数の契約とシナリオを分ける

一回の関数呼び出しの契約は、通常の `.target().it()` で検証します。
encodeとdecodeの往復関係や、同じ関数への二種類の引数を比較するケースは、[複数呼び出しの契約](multiple-calls.md)としてunit側で扱います。
呼び出し回数が複数であることだけを理由に、flowへ移す必要はありません。

flowでは、一連の操作で成立するシナリオ全体を検証します。
通常のcase同士を実行順に依存させず、順序が必要な操作を一つの独立した実行単位にまとめる方針です。

| 確かめたいこと | 検討する入口 |
|---|---|
| 一回の対象呼び出しの引数と結果 | 通常の `.it()` |
| 複数の対象間の関係や、複数入力から分かる関数の性質 | unit側の `.it().calls()` |
| ある前提から操作を順に行ったときの振る舞い | `.flow()`（設計中） |

## 具体的なtargetは必須にしない

E2Eでは画面やHTTPを通じて振る舞いを確かめるため、一つの関数を検証対象として指定できない場合があります。
flowはtargetを必須にせず、シナリオ名で「何をするとどうなるか」を表せる方向です。
targetの代わりになる関数を用意したり、操作からtargetを自動生成したりする必要はありません。

関数・メソッドや関係を明示的な検証対象として付ける場合の契約も、flowの具体的なAPIと合わせて検討します。

## シナリオ全体で扱いたいこと

次の責務を、シナリオ全体の一つの試行として扱うことを検討しています。

- 準備した環境を使って、一連の操作と観測を行う。
- 成功・失敗に応じた後始末を行う。
- timeoutとretryを、一連の操作の実行境界に適用する。
- シナリオとして成功したか、どこで失敗したかを報告する。

これらはflowの目的から検討する責務で、詳細なライフサイクルの契約はまだ確定していません。
外部DB等の初期化を暗黙に行うことは想定しておらず、利用者が準備・後始末を用意します。

## 手順の書き方は設計中

内部の手順を通常のTypeScriptの `async / await`、ローカル変数、関数で書く案を検討しています。
操作ごとのstep名や、`.call().args().saveAs()`による値の管理を必須とする案は見直しています。

操作列を実行前に取り出すこと、操作ごとの観測や診断を提供することが必要かを確かめてから、stepを設けるか、どの粒度まで管理するかを決めます。
`.flow(name, body)`を `.it()`と並ぶ入口にする方向は維持し、bodyの型と検証の書き方は未確定です。

設計上の判断は[判断記録](../concepts/design-review.md#flowのユーザー契約案)を参照してください。
