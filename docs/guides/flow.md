# シナリオ全体を検証するflow

flowは、前提から一連の操作を行い、その契約が成立することを一つの独立したケースとして検証します。例えば作成・更新・取得を順に行い、取得結果が更新内容と一致することを確かめます。

## 関数の契約とシナリオを分ける

一回の対象呼び出しは通常のケースで検証します。往復などの値の関係は[複数呼び出し](multiple-calls.md)で扱い、状態を変える操作の順序に意味がある場合にflowを使います。呼び出しが複数あるだけでflowを要求しません。

通常のケース同士を実行順へ依存させることはできません。順序が必要な操作をflow内へまとめ、他のケースとの順序には依存させません。

## 対象範囲を明示する

操作する公開関数・インターフェースの集合を指定し、その範囲から操作を選びます。E2Eでは画面やHTTPを対象にできます。単一の関数へ包む必要はありませんが、任意の関数をケース内から操作対象へ追加することもできません。

観測のための読み取りは操作と区別します。対象の実装を差し替えたり、観測中に対象の操作を再実行したりする入口にはしません。

## 操作と観測を書く

`new Test().target(scenario({ create, rename, read })).flow(name, t => t.steps(...).expect(...))` と書きます。stepsの全操作を宣言順に実行します。[完結したコード例と禁止例](writing-tests.md#操作列)に従います。

```text
対象範囲: ユーザー作成・更新・取得
前提: ケース用のDB
操作1: Aliceを作成する
操作2: 作成結果のIDを使って名前を変更する
操作3: 同じIDのユーザーを取得する
期待: 取得した名前が変更後の名前と一致する
```

結果をローカルな参照として次の入力に渡し、対象から型を推論します。操作ごとの名前・保存用ID・saveAsを必須にしません。観測は操作列全体を囲みます。各段階の状態を確かめる場合は公開のread操作をstepsに含め、その結果refを返して照合します。一つのケースにすべての責任を詰め込む必要はありません。

## 待機と再実行

非同期の効果には、契約に対応する完了条件または有限の観測期限を指定します。観測を繰り返すことと、targetをもう一度実行することは別です。メール到着を待つために送信処理を再実行しません。

ケース全体のretryでは新しい試行として前提からやり直します。試行timeoutは実行の上限であり、業務上の期限の期待を代替しません。

## 結果と後始末

実行済みの操作、失敗した操作、未実行の操作と、各観測・検証を対応させます。読み取り失敗を不在へ変換したり、未評価の条件を成功扱いにしたりしません。

成功・失敗にかかわらず資源の後始末を行います。外部状態の初期化・復元は環境が提供し、別ケースの結果へ依存させません。復元不能を隠して後続へ進みません。

型と実行時の制約は[UX/DX契約](testing-contracts.md#操作列と時間を記述する)に従います。
