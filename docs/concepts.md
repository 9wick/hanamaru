# 考え方

hanamaruの中心は、**テストの実行計画を作ることと、その計画を実行することの分離**である。
metadataという言葉は、その実行計画を指す。

## テストは値になる

```ts
const tests = new Test()
  .target(add)
  .it('足す', t => t.args(1, 2).expect(e => [e.result.toBe(3)]))

const plan = tests.plan()
const result = await run(plan)
```

ビルダーが対象・引数・モック・期待を組み立てる。
`.plan()` が公開された構造を返し、`run()` がそれを実行する。
CLIもこの境界に従う。

```text
型付きビルダー → TestPlan（metadata） → run → TestResultを含むRunResult
```

計画は「このテストがどういうものか」を表す。
利用目的に応じた解釈は計画を受け取る側に委ね、計画の仕様はテスト自体の構造として定める。

## 計画は実行に必要な構造を持つ

計画には次のものが入る。

- 対象となる関数、またはメソッドと受け手
- ケースごとの準備と後始末
- モックの登録先と振る舞い
- 引数の値、または引数を得る方法
- 正常終了・例外送出のどちらを期待するか
- 各アサーションの対象、比較方法、期待値や述語

関数・オブジェクトへの参照も値として保持する。
構造化されていることとJSONへシリアライズできることは別である。
`callsFake` の関数本体を解析したり、`argsFrom` の結果を取得するためにsetupを実行したりはしない。
「実行時にこの関数で決める」という定義自体が計画に現れる。

[実行計画とmetadata](./metadata.md)で各フィールドを定める。

## 型は書く順序と対応する

```text
new Test()
  ├─ target(...) ────────────────────┐
  └─ setup(...) → target/targetFrom(...) ─┤
                                      ↓
                         describe / 共通mock を設定
                                      ↓
                         最初の it / only / skip / todo
                                      ↓
                         ケース追加 / plan のみ
```

setupはtargetの前に1回、targetは1回だけ。
最初のケースを書いたら共通設定は固定される。
既に型チェックしたケースの前提を、後から別の型へ変える経路をなくす。

ビルダーの各操作は新しい値を返す。設定段階の値を保存して分岐することはできる。
完成済みのテストに設定を上書きする形の派生は提供しない。
別の実装に同じケースを適用する方法は[再利用](./reuse.md)を参照。

## アサーションも計画の要素になる

`e.result.toEqual(v)` は即時に比較せず、比較方法と期待値を持つアサーションを返す。
`.expect()` に渡すコールバックは定義時に1回評価し、返されたアサーションを計画に保存する。
実際の結果を使う述語の実行は後になる。

```ts
.expect(e => [
  e.result.toEqual({ id: 'u1', name: 'Alice' }),
  e.mock('send').calledTimes(1),
])
```

実行器がアサーションを個別に評価するため、失敗をまとめて報告できる。

`e.result` は結果の値ではなく、結果を検証する記述を作るオブジェクトである。
結果の値に触れたいときは `toSatisfy('条件の説明', value => ...)` を使う。

## 正常終了と例外を分ける

`expect` は正常終了、`expectError` は例外送出を宣言する。
モックだけを検証するケースでも、この期待は必ず計画に存在する。

```ts
.expect(e => [e.mock('send').notCalled()])
// 正常終了し、sendが呼ばれないこと。途中で予期せずthrowすれば失敗。
```

`expect` の引数に `error` はなく、`expectError` の引数に `result` はない。
両方の結果を同じケースで期待することはできない。

## 名前付きモック

登録名はケース内のモックを参照するためのキーである。
`.mock('send', mailService, 'send', ...)` で追加すると、`e.mock('send')` が使える。
名前を介して登録先と検証が対応するため、構造の等しい別オブジェクトを誤って検証する経路がない。

計画は登録名に加えて元のオブジェクト・メソッド・振る舞いも保持する。
ケース内の `override` は既存の登録先を維持して振る舞いだけを変える。

## 計画作成にも通常のJavaScriptは動く

`.it()` や `.expect()` のビルダーコールバック、テストモジュールのトップレベルコードは定義時に実行される。
そこへI/Oを書くと、そのI/Oは定義時に起きる。
準備の副作用はsetupへ、実際の検証はアサーションへ置く。

「計画を取得するときにtarget・setupを実行しない」という契約を、
「任意のユーザーコードを含むimport全体に副作用がない」という保証へ広げない。

## 実装の境界

| 部分 | 責務 |
|---|---|
| builder | 型付きの操作を正規化されたTestPlanへまとめる |
| loader / CLI | ファイルを読み込み、完成済みの定義から計画を集める |
| engine (`run`) | 計画に従い準備・呼び出し・検証・復元を行う |
| reporter | 実行結果を整形する |

ランタイムの依存パッケージ0は実装上の目標である。
公開する計画と、その実行セマンティクスを中心に設計する。
